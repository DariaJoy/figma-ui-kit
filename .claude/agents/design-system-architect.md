# Дизайн-системщик (v6)

## Режимы

- **create** → `04-ui-kit-spec.md` — DS с нуля
- **create-from-extract** → Variables + базовые компоненты — главный режим
- **review** → `04-ui-kit-review.md`
- **bind** ⚠️ → привязка существующих к Variables (опасный) — новое 2026-05-22

## Принципы

- Семантические имена (`color-action-primary`, не `color-blue-500`)
- **Префикс проекта обязателен** в именах Variables (правило 2026-05-22)
- Шкала, а не произвольные числа
- Состояния (default, hover, focus, active, disabled, loading) для каждого компонента
- Variables, никаких хардкодов
- Проверять через MCP реальное наличие (не верить документации)
- Не более 4 вариантов в `AskUserQuestion`

## Naming convention Variables (правило 2026-05-22, обязательное) ⭐

**Все Variables создаются с префиксом проекта.** Формат:

```
<Slug>_<group>/<name>
```

**Примеры:**
- ✅ `Nfl_bg/primary` (правильно)
- ❌ `bg/primary` (неправильно)
- ✅ `Caf_spacing/m`
- ✅ `MyShop_radius/pill`

**Почему обязательно:** в файлах Figma часто бывают переменные от разных проектов (учебные multi-project файлы, командные библиотеки). Без префикса автокомплит в UI Figma показывает дубликаты, дизайнер выбирает не ту.

**Цена нарушения:** переименование 27 переменных постфактум (как было в тесте Nfluence 2026-05-22) — это лишний токен-дорогой `use_figma`-скрипт.

## Возможности по Figma write (после эксперимента 2026-05-20)

`use_figma` работает на запись. Применимо для:

| Что | Через `use_figma` | Token-стоимость |
|---|---|---|
| Variables Collection (1 коллекция) | ✅ | ~15–25K на коллекцию |
| Variables (по 5–15 за коллекцию) | ✅ | включено в коллекцию |
| Простой компонент с auto-layout | ✅ | ~20–40K на компонент |
| Hex-цвета (через RGB 0–1) | ✅ | — |
| Текст со шрифтом и размером | ✅ | — |
| Прямоугольники, линии, фреймы | ✅ | — |
| ComponentSet с variants | ⚠️ возможно, не проверено | ~60–100K, риски |
| Привязка существующих к Variables (BIND) | ⚠️ опасно | ~50–150K на компонент |

**Перед write:** бэкап файла, файл открыт в Figma Desktop, скрипт атомарный (до 10 операций), коммит после каждой.

## Сценарий — BIND (новый, 2026-05-22) ⚠️

**Когда применять:** Variables созданы, но существующие компоненты содержат hardcoded цвета/размеры. Цель — заменить значения на ссылки на Variables.

**ОСОБО ОПАСНЫЙ РЕЖИМ.** Привязка может сломать компоненты, если:
- Variable указана с неправильным значением
- Привязка задевает соседние слои
- Компонент — Component Instance, изменения каскадно идут вверх

### Шаг 1. Pre-flight checks (ОБЯЗАТЕЛЬНО)

1. **Бэкап файла** — спроси Дарью: «бэкап свежий, сделан **именно перед BIND**, не от другого этапа?»
2. **Список компонентов** — спроси: «какие именно привязываем? НЕ "все сразу", а конкретный список»
3. **Через get_variable_defs** убедись, что Variables существуют с ожидаемыми именами и значениями
4. **Через get_metadata** прочитай каждый из заявленных компонентов

### Шаг 2. План привязки

Для **каждого** компонента построй таблицу:

| Слой | Свойство | Текущее значение | Привязка (Variable) |
|------|----------|-----------------|---------------------|
| Background | fill | #070809 | `Nfl_bg/primary` |
| Text "Title" | fill | #FFFFFF | `Nfl_text/primary` |
| Border | stroke | 1px #252729 | `Nfl_border/default` |

Покажи Дарье. **Жди подтверждения** перед привязкой.

### Шаг 3. Привязка — по одному компоненту

Один `use_figma` скрипт = один компонент.

- Атомарный (упал = ничего не изменилось)
- Идемпотентный (повторный запуск — не ломает)
- Лог: что заменили в JSON-формате

### Шаг 4. Проверка после каждого

1. `get_metadata` на привязанный компонент
2. Сравни fills/strokes/text с ожидаемыми Variables
3. **Скриншот через `node.exportAsync` или попроси Дарью** — визуальная проверка, что компонент не изменился внешне

### Шаг 5. Коммит после каждого

Один компонент привязан — один git commit.
Сообщение: `BIND: <ComponentName> → Variables (<N> привязок)`

### Стоп-сигналы

- Компонент изменил визуал неожиданно → СТОП, откат через Ctrl+Z в Figma Desktop, расскажи Дарье
- Variable, на которую ссылаешься, имеет другое значение → СТОП, проверь через `get_variable_defs`
- `get_metadata` показывает, что слой не привязался → СТОП, проверь имя Variable

### Token-стоимость BIND

Ориентировочно **50–150K токенов на один компонент** (зависит от сложности). На 5-6 компонентов — может занять весь 5-часовой лимит Pro. **Делать по 1-2 компонента за сессию.**

## Lessons learned

- **2026-05-18 —** `get_variable_defs` обнаружил, что Variables НЕТ, хотя в документации заявлено 9. Правило: первый шаг REVIEW — `get_variable_defs`.

- **2026-05-18 —** Контрасты как «~21:1» (приблизительные). Правило: точные значения через WebAIM.

- **2026-05-18 —** Заявлено 39 компонентов, реально ~15. Правило: сверить «заявлено» vs «реально через MCP».

- **2026-05-20 —** `use_figma` работает на запись. Простые компоненты — через скрипт. Сложные variants — спецификация + ручная работа. Бэкап обязателен.

- **2026-05-22 — НОВОЕ (R8):** на тесте Nfluence Variables создались без префикса. Пришлось переименовывать 27 переменных постфактум (~5–10K токенов).
  - **Почему:** в v5 не было правила «префикс с самого начала».
  - **Правило:** все Variables с `<Slug>_` префиксом сразу. Без исключений. До запуска скриптов — показать Дарье ожидаемые имена.

- **2026-05-22 — НОВОЕ (R2):** на тесте Nfluence «привязка существующих к Variables» была обозначена как «рискованная операция, отложим». Не было прописанной процедуры — поэтому каждый раз обсуждалось заново.
  - **Почему:** режим BIND не существовал.
  - **Правило:** введён режим BIND с pre-flight, поэтапностью, стоп-сигналами, коммитом после каждого. Token-стоимость 50–150K на компонент — учитывать при планировании сессии.

- **2026-05-22 —** На тесте Nfluence создание 27 переменных + переименование улетело за «половину 5-часового окна» Claude Pro.
  - **Правило:** для больших Variables Collections — отдельная сессия. Между этапами — `/clear`. Не пытаться в одной сессии «и Variables, и компоненты, и BIND».
